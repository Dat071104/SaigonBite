The diagrams use UML associations with SQL multiplicities. \texttt{PK} marks primary-key columns, \texttt{FK} marks foreign keys, \texttt{U} marks a single-column UNIQUE constraint, \texttt{U*} marks membership in a composite or partial unique constraint, \texttt{C} marks a column participating in a CHECK, and \texttt{?} marks a nullable column. Full SQL types, NULL rules, CHECK expressions, key declarations, and enforcement notes are in the class-to-table mapping.

The mapping has one primary row for each of the 110 C0 columns. It also makes non-column correspondences explicit: \texttt{Order.\allowbreak{}lines} maps to the child \texttt{order\_\allowbreak{}line.\allowbreak{}order\_\allowbreak{}id} relationship; \texttt{HubMenuItem.\allowbreak{}item} maps to \texttt{hub\_\allowbreak{}menu\_\allowbreak{}item.\allowbreak{}menu\_\allowbreak{}item\_\allowbreak{}id}; \texttt{Order.\allowbreak{}item\_\allowbreak{}subtotal} and \texttt{Order.\allowbreak{}total} are derived properties with persisted columns; \texttt{MenuItem.\allowbreak{}brand\_\allowbreak{}name} is a joined projection of \texttt{brand.\allowbreak{}name}; \texttt{LocalCustomer} and \texttt{TouristCustomer} map to the same \texttt{customer.\allowbreak{}customer\_\allowbreak{}type} discriminator; and \texttt{OrderLine.\allowbreak{}line\_\allowbreak{}total} is computed, with no SQL column. At C0, \texttt{UserAccount.\allowbreak{}created\_\allowbreak{}at} was a design gap and the column was absent. Its later P4.1 disposition and scoped test evidence appear in Table P4-1 and the detailed resolution appendix.

\texttt{Customer} is stored in one \texttt{customer} table. Its \texttt{customer\_\allowbreak{}type} CHECK distinguishes \texttt{LOCAL} from \texttt{TOURIST}; it does not create separate subtype tables. \texttt{hub\_\allowbreak{}menu\_\allowbreak{}item} is the association-class table between Hub and MenuItem, with a composite primary key on \texttt{(hub\_\allowbreak{}id, menu\_\allowbreak{}item\_\allowbreak{}id)}. There is no Shipper table: \texttt{delivery.\allowbreak{}shipper\_\allowbreak{}id} references \texttt{user\_\allowbreak{}account.\allowbreak{}id}, and the SHIPPER role is held by the linked account. \texttt{Quote}, report filters and rows, and receipts are computed views rather than persisted classes.

The UNIQUE rules are \texttt{hub.\allowbreak{}code}, \texttt{brand.\allowbreak{}name}, \texttt{user\_\allowbreak{}account.\allowbreak{}username}, \texttt{customer.\allowbreak{}user\_\allowbreak{}id}, \texttt{voucher.\allowbreak{}code}, \texttt{orders.\allowbreak{}idempotency\_\allowbreak{}token}, \texttt{payment.\allowbreak{}order\_\allowbreak{}id}, and \texttt{delivery.\allowbreak{}order\_\allowbreak{}id}; the composite rules are \texttt{menu\_\allowbreak{}item(brand\_\allowbreak{}id, name)}, \texttt{hub\_\allowbreak{}menu\_\allowbreak{}item(hub\_\allowbreak{}id, menu\_\allowbreak{}item\_\allowbreak{}id)} as its primary key, and \texttt{order\_\allowbreak{}line(order\_\allowbreak{}id, menu\_\allowbreak{}item\_\allowbreak{}id)}. The partial unique index \texttt{idx\_\allowbreak{}offer\_\allowbreak{}one\_\allowbreak{}open} limits each order to one \texttt{replacement\_\allowbreak{}offer} whose state is \texttt{OFFERED}; resolved offers remain stored history. The unique child FKs on \texttt{payment.\allowbreak{}order\_\allowbreak{}id} and \texttt{delivery.\allowbreak{}order\_\allowbreak{}id} cap each Order at one child row but do not require presence. The SQL also permits an Order with zero OrderLine rows. The contract requires checkout to create one Payment and at least one OrderLine, and \texttt{markReady} to create a Delivery; these application-path requirements were assigned to P4 verification, not inferred from the FKs; recorded test evidence is in Section 5.1. P2-S09 records the related cross-row guards, including same-order offer/line ownership and shipper eligibility.

Money is stored as whole VND where applicable. For an Order, \texttt{item\_\allowbreak{}subtotal} is S, \texttt{voucher\_\allowbreak{}discount} is D, \texttt{delivery\_\allowbreak{}fee} is F, \texttt{quiet\_\allowbreak{}discount} is Q, and \texttt{total\_\allowbreak{}amount} is T, constrained by \texttt{T = S \ensuremath{-} D + F \ensuremath{-} Q}. \texttt{payment.\allowbreak{}amount} holds the COD amount due or captured online amount C; \texttt{refund\_\allowbreak{}amount} is an amount owed, not paid out. An accepted replacement can leave a partial online obligation \texttt{C \ensuremath{-} T}; an unfulfilled online order is owed the full C. \texttt{delivery.\allowbreak{}cash\_\allowbreak{}collected} records cash at delivery, which must equal T for COD completion. Order-line and replacement-offer names/prices are snapshots; later catalogue edits do not rewrite the existing order history.

Event columns ending in \texttt{\_\allowbreak{}at} are UTC timestamp text. \texttt{voucher.\allowbreak{}valid\_\allowbreak{}from} and \texttt{valid\_\allowbreak{}until} are inclusive Asia/Ho\_Chi\_Minh calendar dates stored as text, not UTC instants. The archive timestamps are on Hub, Brand, MenuItem, Address, Voucher and Order. \texttt{user\_\allowbreak{}account.\allowbreak{}is\_\allowbreak{}active} is an account lifecycle flag, not an archive timestamp; unlisting a HubMenuItem deletes the association row. Under the plan's archive rule, an archived parent is hidden from operational lists while authorized history, receipts, reports and refund obligations remain available. Child order lines, payments, deliveries and offers remain attached to the retained Order. These retention rules were design requirements for P4 verification, not behaviors inferred from a flag alone. Later test evidence is in Section 5.1.

The marked items were design targets not yet in code at C0. Their later P4 disposition is recorded in Table P4-1. \texttt{P2-S02} requires \texttt{user\_\allowbreak{}account.\allowbreak{}created\_\allowbreak{}at}, which is absent from both the draft class and SQL table and is assigned to P4.1. \texttt{P2-S03} requires the Tourist CHECK to require \texttt{nationality}; the nullable column exists, and the static Phase 2 review found controller validation, but the SQL CHECK does not enforce it. \texttt{P2-S07} requires the linked Customer account to have role \texttt{CUSTOMER}; the FK and UNIQUE rule do not enforce that role. P4.7 was adopted as the account subphase for S03/S07. The figure's historical legend identifies the C0 design targets and P4 inputs P2-S02/S03/S07.

\texttt{P2-S08} is not a missing-value defect: \texttt{Payment.\allowbreak{}updated\_\allowbreak{}at} is \texttt{Optional[str]} in the domain model but \texttt{NOT NULL} in SQL, and the \texttt{PaymentDAO.\allowbreak{}insert} AST body writes the supplied \texttt{updated\_\allowbreak{}at} or falls back to \texttt{created\_\allowbreak{}at}. The SQL CHECK also permits Payment values \texttt{FAILED} and \texttt{REFUNDED}; per P2-S01 and plan \S{}4.3 these remain deferred or unreachable. No declined-payment row or refund-payout path is added to this mapping.
