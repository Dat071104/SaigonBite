The following eight operations expand the corresponding report III design sequences with the actual DAO responsibilities and the database resource. Their SSD operation names, parameter strings and occurrence pointers are unchanged. Each set of Parts A--\ldots{} is one request; a continuation does not start another operation or a new transaction. Focused plates retain the actor, view and controller, show the relevant domain/helper/value lifelines, and add the relevant DAOs and \texttt{:Database}. This resource is not an application class. Mechanical object loading is scoped in the responsibility table below so the high-risk writes remain readable.

The design baseline was C0 \texttt{45ac76221b0a103174c7c01d17577e6e49cfd665}. A dagger in a diagram marks a target at that baseline; Table P4-1 records its final status and scoped evidence.

For writes, the transaction extends from \texttt{BEGIN IMMEDIATE} to successful \texttt{COMMIT}, including all intended DAO writes. Every conditional DAO boolean is checked by the controller or its named helper. A guard failure, zero rowcount or false save result stops subsequent writes and rolls back the active transaction. A write or COMMIT error rolls back if a transaction remains active. A failed BEGIN does not trigger an unconditional ROLLBACK. An exhausted \texttt{database is locked} outcome produces \textbf{``Busy, please retry; nothing was changed''}. P2-S13/P3-S03 identified incomplete controller/helper and commit-failure handling at C0; final status is in Table P4-1. The summary band is a transaction key, not control flow. Actual \texttt{opt}, \texttt{loop} and \texttt{break} rectangles enclose the messages their guards control. A \texttt{break} operand ends the enclosing request: successful returns cannot fall through into compensation, and early refusals skip later writes. Named continuation operands repeat the guard on the next plate; a failure handler is an exclusive continuation rather than the next step of a successful request.

The connection configuration uses \texttt{foreign\_keys=ON}, \texttt{journal\_mode=WAL}, \texttt{synchronous=NORMAL}, and \texttt{busy\_timeout=10000}; the P4 foundation tests check the resulting settings on their test connection (Table P4-1 and its detailed appendix). No user interaction or external request occurs while a write lock is held; the checkout simulator decision is a short deterministic local call.

\textbf{UC-01 --- confirmCheckout (\texttt{OP-01})}

A new token revalidates the owner/address, active hub and catalogue, current load/capacity, quantities, voucher and raw distance inside the write transaction. \texttt{Quote.fingerprint(payment.method, payment.option)} takes the pure-domain enums carried by the real \texttt{PaymentChoice} fields. Both full fingerprint and T must match consent (F-07); the F-04 radius/fee decision uses raw distance. An own-token replay returns the existing order without authorization, repricing or insertion; a foreign token is refused without disclosure. ONLINE decline saves zero Order/Line/Payment rows. Successful checkout inserts one order header, its N snapshots and one payment; it does not simulate a conditional state UPDATE. COD is PENDING, ONLINE is PAID with C=T. P2-S05 releases authorization on every later failure through COMMIT. UC01-PC01\ldots{}PC06 and MG01\ldots{}MG03 are the contract anchors.

SSD parameters: \texttt{hubId, addressId, lines(itemId, quantity), voucherCode?, paymentMethod, onlineOption?, simulatorOutcome?, quoteFingerprint, quotedTotal, checkoutToken}. Occurrence: \texttt{models/UC-01/ssd\_uc01\_PartB.drawio\#01S-M04}.

\textbf{UC-02 --- takeDelivery (\texttt{OP-10})}

DeliveryDAO.take uses the actual AWAITING\_PICKUP predicate; a true rowcount result is required before the paired READY\ensuremath{\rightarrow}OUT\_FOR\_DELIVERY save. Any later failure rolls back the pickup as well. Only one competing take may commit; this is the design guarantee. The later browser race checks are recorded in Sections 4.3.6 and 5.1. No additional one-active-delivery rule is introduced.

\textbf{Guarded interaction control after independent review}

The checkout token-exists operand ends with replay/refusal and skips all authorization/repricing/INSERT work. The ONLINE-decline break contains rollback and its refusal return. Only COD or approved ONLINE enters the write continuation. Part G separates the successful COMMIT return in a terminal break from the failure break containing conditional authorization release, active-transaction rollback and mutually exclusive Busy/controlled-refusal replies. An approved success never reaches the release call.

For accepted replacement, Part C is the invalid-target break: it contains the exact-offer WITHDRAWN call, SQL request and checked result. A false result encloses rollback/refusal in its own break; a true result encloses the intended withdrawal-only COMMIT and result return. This break ends the request. Valid-target Parts D--F explicitly skip that operand, enclose the line/totals/payment/ACCEPTED work in continued valid-target operands, and end at the successful COMMIT/result. Their checked-save failures enter Part G's exclusive failure break, never the successful withdrawal branch.

Other write operations use the same explicit success-END versus failure-handler continuation. The final failure plate contains the actual rollback request and Busy/refusal returns inside guarded regions; rollback is optional only when a transaction is active, including the failed-BEGIN case with no active transaction. The sales-report denial and invalid-date operands terminate before report queries; all report branches remain read-only. Synchronous method and database request arrows have closed filled heads in editable XML, SVG and PNG; replies remain dashed with open heads. Attribute/property note arrows retain their separate annotation role.
